# Developing Gantry

How to build, test and change Gantry. The [PRD](product-requirements-document/gantry.md), [glossary](../GLOSSARY.md) and [ADRs](architectural-decision-record/) are binding on every change. [How Gantry works](architecture.md) has the architecture and the repository layout.

## What you need

- Rust 1.99.1 (pinned in `rust-toolchain.toml`, with clippy and rustfmt).
- A C/C++ compiler: MSVC on Windows, gcc or clang elsewhere. The X1 camera's H.264 decoder (OpenH264) and SQLite are compiled in.
- Node 26 and pnpm 12, for the frontend, the desktop app's tooling, the website build and the Sandcastle harness.
- Docker, only for the printer simulators and building the image.

```bash
pnpm install
pnpm --filter @gantry/web build        # the React app, into web/dist, which the binary embeds
export GANTRY_SECRET_KEY="a development key, never a real one"
cargo run -- user create --admin --username admin
cargo run                              # http://127.0.0.1:8080
pnpm --filter @gantry/web dev          # optional: Vite with hot reload, proxying the API to cargo run
```

On Windows, use the MSVC toolchain (`RUSTUP_TOOLCHAIN=1.99.1-x86_64-pc-windows-msvc`) unless MinGW is installed.

## The local gate

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
pnpm --filter @gantry/web lint
pnpm --filter @gantry/web test
pnpm --filter @gantry/web build
pnpm --filter @gantry/web e2e     # Playwright against the real binary: local only, never in Actions
```

CI runs all but the last on every pull request ([`ci.yml`](../.github/workflows/ci.yml)), so run Playwright locally before merging. The first Playwright run needs a browser: `pnpm --filter @gantry/web exec playwright install chromium`. The desktop app's checks run in `desktop/src-tauri` (`cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`), and in CI by [`desktop.yml`](../.github/workflows/desktop.yml) when `desktop/` changes.

The Print Files the tests upload are generated by `crates/test-support/print-files`. After changing them, write the Playwright copies again with `cargo run -p gantry-print-file-fixtures --bin write-e2e-fixtures`; a test fails while they are stale.

## Developing without a printer

No printer is owned yet, so everything is built to work without one:

- **Simulated Driver:** ships in the binary. Add "Simulated" Printers in the UI and control their speed, Faults, filament and dropouts, plus a test camera stream. It drives the whole dashboard, login, Queue and Alerts flow.
- **Mock Bambu broker:** an MQTT-over-TLS broker that replays real `report` payloads, so the Bambu Driver can be tested in CI.
- **Mock Bambu cameras:** a P1/A1 camera (TLS, JPEG frames) and an X1 camera (RTSPS, H.264 generated at start), so both camera sources are tested without a printer.
- **Mock Bambu FTPS server:** implicit TLS on a local port, with session reuse required as on the printer, so upload-and-start is tested without one.
- **Simulated Klipper and OctoPrint's virtual printer** in Docker for those Drivers: `docker compose -f docker/simulators/compose.yaml up -d`, then [their tests](processes/testing-drivers-with-simulators.md). Local only, never in Actions.
- **Mock PrusaLink, Duet and SDCP servers**, written from those protocols' documentation.

What a simulator can't prove (real firmware behaviour, real camera streams, FTPS upload) is called out as unverified in each pull request.

## Screenshots

The screenshots in [`docs/images/`](images/), used by the README, these docs and the website, are taken from a real Gantry with a demo Fleet of Simulated Printers:

```bash
pnpm --filter @gantry/web build && cargo build -p gantry
pnpm --filter @gantry/web screenshots     # GANTRY_EXE=<path> to use another binary
```

[`web/scripts/screenshots.mjs`](../web/scripts/screenshots.mjs) starts the binary with a throwaway data directory, adds the Printers, Print Files, Jobs and Queue, and captures each page in Chromium. Take them again after a visible change to the dashboard.

## The website

The project website, [gantry.adrianeyre.co.uk](https://gantry.adrianeyre.co.uk), is the `@gantry/site` package in [`site/`](../site/), built with Vite and published to GitHub Pages by [`pages.yml`](../.github/workflows/pages.yml): when `site/`, `docs/images/`, the icons or the lockfile change on `main`, after each release, or by hand.

```bash
pnpm --filter @gantry/site dev       # http://localhost:5174
pnpm --filter @gantry/site test      # the release placeholders
pnpm --filter @gantry/site build     # typechecks, then into site/dist/
gh release view --json tagName,url,publishedAt,assets > release.json
GANTRY_RELEASE=release.json pnpm --filter @gantry/site build   # download buttons linked to that release
```

[`site/index.html`](../site/index.html) is the page, written as static HTML so it reads without JavaScript. Its product pictures are [Stageshow](https://github.com/benjitaylor/skills/tree/main/stageshow) demos (React, in [`site/src/demos/`](../site/src/demos/)): mock-ups of Gantry's own pages, styled with its Cobalt theme, that play one short story each as they scroll into view. [`site/src/main.tsx`](../site/src/main.tsx) mounts each into its `[data-demo]` slot, replacing the screenshot or blank that stands in for it without JavaScript; under reduced motion each shows its finished frame. The kit is vendored in [`site/src/kit/`](../site/src/kit/) (see its `VENDORED.md`).

The build copies in the screenshots and icons, fills in the page's `{{PLACEHOLDERS}}` from [`site/release.mjs`](../site/release.mjs), and fails on an unknown placeholder or a link to a file it didn't build. The page follows the system's light or dark mode and keeps WCAG AA contrast. When a demo changes, film it with Stageshow's `scripts/film.mjs --gate` against `pnpm --filter @gantry/site dev` at `?mount=all` (every demo mounts at once, since the filmer doesn't scroll), at 1280 and 390 wide.

The custom domain is set in the repository's Pages settings (Settings → Pages → Custom domain) once its DNS has a `CNAME` record for `gantry.adrianeyre.co.uk` pointing at `adrianeyre.github.io`; [`site/public/CNAME`](../site/public/CNAME) records it. Until then the site is at `adrianeyre.github.io/<repository>/`, which works because the build's links are relative.

## Releases

Each merge to `main` that passes CI is released by semantic-release from its conventional commits: the Docker image, the binaries and the desktop installers ([Releasing](processes/releasing.md)). So write each commit (or squash-merge title) as a conventional commit.

## Contributing with Sandcastle

Issues are worked by a coding agent inside a Docker sandbox using [Sandcastle](https://github.com/mattpocock/sandcastle), and a person reviews and lands the result. Node 26+ and pnpm are needed for this harness:

```bash
pnpm install
cp .sandcastle/.env.example .sandcastle/.env    # then fill in credentials
pnpm exec sandcastle docker build-image
git fetch origin && git checkout -b issue-4-walking-skeleton origin/main
pnpm sandcastle 4                               # work issue #4 in the sandbox
```

[Running Sandcastle](processes/running-sandcastle.md) covers setup, credentials, writing prompts, landing a run and troubleshooting. No printer credential, access code or serial number ever goes into a prompt, log or commit.
