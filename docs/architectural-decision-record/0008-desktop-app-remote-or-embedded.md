# The desktop app is a window onto a server, remote or embedded; the embedded secret key lives in the OS keychain

The Tauri desktop app has two modes. In **remote** mode it is a client of a Gantry server the person chooses: a small page bundled with the app takes the address, the app checks it is Gantry (`/healthz` answers `ok`, `/api/session` asks for a login) and sends the window there, so the dashboard and login page are the ones that server embeds (ADR-0002), never a copy. In **embedded** mode the app runs the same core and server in-process, listening only on 127.0.0.1, with the default Drivers and its data in the app's data folder, and sends the window there in the same way. We rejected bundling the React app into the desktop app, because two copies of the UI would drift from the servers they talk to.

The embedded server's secret key (ADR-0005) is generated on first run and kept in the OS keychain (Credential Manager, the macOS Keychain, the Secret Service on Linux), never beside the database, so a copied data folder doesn't carry the key to its Printer credentials. Where there is no keychain, the `GANTRY_SECRET_KEY` environment variable is used instead; with neither, embedded mode refuses to start and says so, as Gantry does. We rejected a key file in the app's folders as the fallback, because it would sit beside the database it protects.

Embedded mode may create the first Admin from the bundled page when no account exists, which a server never offers (PRD §9.2): the embedded server is reachable only from the same machine, so no stranger can claim it. Only the bundled page can call the app's commands. A server's pages are given one thing at runtime, for their own origin alone: Tauri's notification plugin, so a desktop Alert channel can show native notifications. Links to anywhere else open in the system browser.
